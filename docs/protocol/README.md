## 报文总体结构

两份接口规范使用同一报文骨架：`长度 + 命令码 + 报文信息 + LRC`，LRC 校验范围为「命令码 + 报文信息」。OTA 侧字段以 ASCII 定长串为主（右补空格或左补 0），激活与密钥下载侧字段以 HEX 为主（补 0x00）。

## 关键时序与时限

| 约束 | 出处 |
| --- | --- |
| 终端启动后 10 分钟内未完成激活即销毁密钥并结束通讯 | 激活 · A0 |
| 服务器下发握手响应后 5 分钟内未收到激活请求，断开连接并清除握手数据 | 激活 · A0 |
| 认证完成后 10 分钟内未完成密钥下载即销毁密钥 | 激活 · A2 |
| TransKey = RandomA xor RandomB，后续数据走 AES；KBPK（AES256）用于密钥加密与 MAC，加密／MAC 子密钥按 CMAC 方式派生 | 激活 · A2 |
| 密钥下载按索引逐个下发，KCV 未回则从最小未确认索引重发，同一密钥最多重发 3 次 | 激活 · A3、RKI · F—G |
| 响应码 99 要求终端发起状态更新；状态设置报文需用 Term_SK 对 SN＋终端状态＋双方随机数签名 | OTA · 13 |

## 待确认问题

阅读三份文档时发现的不一致与缺口，实现前需与终端侧确认，暂不改动原文：

1. **响应码表不统一**：OTA 文档为 00—10、99；激活文档追加 11（授权码不合法）、12（认证超时）、13（验签失败）、14（传输密钥无效）、15（数据域错误）、88（密钥下载完成）。07 在两份文档中分别是「未知通知类型」和「未知类型」。需要一张合并后的全局响应码表。
2. **字段命名错位**：OTA 下载接口请求报文、激活接口激活报文的命令码字段都写成 `responseCode`；激活响应报文出现两行 `orderCode`（分别是命令码与响应码）。属原文笔误，接口实现需按位置而非字段名对齐。
3. **A3 请求密文长度**：`ReqEncData` 声明长度 16，但明文 M＝终端状态(4)＋密钥索引(2)＋NextPack(1)＋上包 KCV(4)＋随机数 R(8)＋随机数(13)＝32 字节，AES 后仍为 32 字节。长度需按 32 修正或明确为变长。
4. **A0 响应加密密钥未定义**：`CipherData` 描述为「用密钥 K 对 M 进行 AES 加密」，K 未定义，按上下文应为终端上送的 TransKey。
5. **授权码发放渠道**：激活文档写「服务器认证用户权限后直接发送到申请人邮箱」，与《TMS 系统功能清单》本期结论（不做邮件服务，授权码在页面申请后交激活工具使用）冲突，以功能清单为准。
6. **KeyType 位段留空**：bit4—6、bit13—15 未定义，bit7 为 RSA 密钥下发方式开关（0＝TR-31，1＝直接下发）。扩展前需确认保留位含义。
7. **签到接口未定稿**：OTA 文档目录含「签到接口」，正文为空；接口列表只列更新／下载／通知三项，未含命令码 13 的状态设置。
8. **RKI 密钥种类**：方案正文称「向终端分配三种密钥」，随后列出 DUKPT IPEK、MK、Fixed Key、RSA Key 四项。
9. **终端状态取值**：协议侧举例为 debug／product／Lock／factory，与功能清单的调试／产品／锁定／工厂对应，但未给出四字节编码取值，需补充枚举与字节定义。
